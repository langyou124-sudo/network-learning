## 四、本地模型方案

### 你的配置评估

| 部件 | 型号 | 对本项目的意义 |
|---|---|---|
| CPU | R7 7800X3D（8C16T，3D V-Cache） | 跑 bge-m3 这种小 embedding 模型 CPU 就够；对话模型主要看显卡 |
| 显卡 | RX 9070 GRE 12GB | 12GB 显存可跑 7B–14B（Q4）；32B（Q4 约 20GB）跑不动 |
| 内存 | 光威 24G DDR5 5600 ×1（待确认） | 若只有 24GB，跑 14B 时浏览器 + dev server 会比较紧 |
| 硬盘 | 梵想 1TB M.2 | 够（模型单个数 GB 到 40GB） |
| 电源 | 600W | 够（9070 GRE 约 200W，CPU 约 120W） |

**结论：能满足，但定位是"小模型"**——embedding 完全没问题，对话建议 14B 以内。

### 两个现实约束

1. **AMD 显卡在 Windows 上的生态**：ROCm 对 9070 系列（RDNA4）的 Windows 支持滞后，
   实际更稳的是 **Vulkan 后端**（LM Studio 自动选，或 llama.cpp 的 Vulkan 构建）。
2. **向量维度**：`knowledge_chunks.embedding` 现在是 `vector(2048)`。
   本地 `bge-m3` 是 **1024 维**，直接写入会被 Postgres 拒，必须先改列。

### 落地方案（Ollama + bge-m3）

```bash
ollama pull bge-m3          # 约 1.2GB，1024 维
ollama pull qwen3:14b       # 对话模型，Q4 约 9GB，能放进 12GB 显存
```

`.env.local`：

```bash
EMBEDDING_PROVIDER=openai
EMBEDDING_BASE_URL=http://localhost:11434/v1
EMBEDDING_MODEL=bge-m3
EMBEDDING_API_KEY=ollama            # 占位，Ollama 不校验
EMBEDDING_DIMENSIONS=1024
```

改维度（Supabase SQL Editor，先看清楚再动）：

```sql
-- 1) 看当前列类型和函数签名
select format_type(atttypid, atttypmod)
from pg_attribute
where attrelid = 'knowledge_chunks'::regclass and attname = 'embedding';

select pg_get_functiondef(oid) from pg_proc where proname = 'search_knowledge';

-- 2) 改列（会清空数据，反正要重灌）
alter table knowledge_chunks alter column embedding type vector(1024);

-- 3) 若原来有 ivfflat / hnsw 索引，需要按新维度重建
```

然后重灌：

```bash
npm run content:embed                      # dry-run，确认 3710 块
npm run content:embed -- --write --reset   # 清空并全量写入
```

预计 3710 次本地 embedding 调用，7800X3D 上大约十几分钟（GPU 更快）。

### 对话模型接进来需要改代码

现在 `src/app/api/v1/chat/route.ts` 写死了小米 MiMo 的 **Anthropic 格式**端点。
换成 Ollama 需要改成 OpenAI 兼容格式（`/v1/chat/completions`），并去掉 `anthropic-version` 头、
把 `system` 从顶层字段挪进 `messages[0]`。这一步还没做，是明确的待办。
